# K リメイク 要件定義書

> 版: v0.4（2026-09-25、D-1〜D-5 と追加の決定事項を反映）/ 前提資料: [00_project-context.md](00_project-context.md), [01_legacy-analysis.md](01_legacy-analysis.md)
> 「【仮】」は旧作に情報が無く、新しく決めた値。遊んでから調整する。

---

## 1. 方針

- **クエスト（PvE）を最優先**で作る。PvP（15thクノット）は第 2 段階。課金・広告は後回し。
- ゲームの核（決定論的な敵パターン、リターン、必殺技による書き換え、最終ターンの即死技、3 すくみ属性、日替わり天気）は**旧作のルールと数値をそのまま再現**する。
- 旧作の技術的な問題は直す。
  - 育成データ・通貨は**サーバを正**とする（端末に保存しない）
  - クエストのクリアは**サーバで検証**する（改ざん対策）
  - マスタデータは**リポジトリで管理**する（`legacy/data` を元に作る）

## 3. 機能要件（フェーズ 1）

### F-01 アカウント
- 初回起動時に名前（最大 6 文字）を入れるとゲストアカウントを作る。
- 端末にトークンを保存して自動でログインする。
- 名前はあとで変更できる。
- 端末を変えたり、ブラウザのデータを消したりするとアカウントは失われる。フェーズ 1 ではこれを許容し、引き継ぎはフェーズ 3 で対応する。

### F-02 ホーム
- 今日の天気、プレイヤー Lv、所持お札数、出撃キャラを表示する。
- 天気は **全プレイヤー共通**。日本時間の 0 時にサーバーが重み付きで 1 つ抽選する（D-3）。
- バトルのステータスは、クエストを開始した時点の天気で確定する（途中で日付が変わっても変えない）。

### F-03 クエスト一覧
- メインクエスト: Lv の数だけ解放。クリア済みかを表示する。解放順は旧作 DB の並び（A, B, C, D, E, F, G, I(→I2), J, L, M, N, O, R, S, T, U, V, X, Y, Z, Dawn, Moi, Nomb）（D-5）。
- メインクエスト I と I2 は **1 回のバトルの中の連戦**として扱う（旧作どおり。§4）。
- お天気クエスト: 今日の天気に対応する 1 件だけ挑戦できる。
- 出撃キャラを 1 体選んで開始する。

### F-04 バトル（詳細は §4）
- 旧作のクエストバトルを完全に再現する。
- リタイア（メニューへ戻る）は負けと同じ扱い（報酬なし）。
- クエストのセッションは 1 人 1 つ。新しく始めると前のセッションは無効になる。有効期限は 24 時間。結果は 1 セッションにつき 1 回だけ受け付ける。
- 操作: 攻撃 / 防御 / 攻撃バフ / 防御バフ / チェック / リターン / 必殺技 / みえーるみえーる / ログ / リタイア
- 勝ったらクリア報酬へ、負けたら敗北画面へ進む。

### F-05 クリア報酬・Lv
- メインクエストを初めてクリアすると Lv+1。偶数 Lv になったらお札 +【仮】1。
- Lv の上限はメインクエストの数（全部を初クリアしたら上がらない。クエストを追加すれば上限も上がる）。
- 敵キャラを仲間にする: 【仮】初クリアは確定、2 回目以降は 20%。
- 既に持っているキャラが出たら「被り」になり、ランダムで 1 ステータスの被りカウント +1（上限はキャラごと）。
- お天気クエストをクリアすると、その属性の強化アイテムを【仮】ランダムに 1〜3 個もらえる。

### F-06 所持キャラ・キャラ詳細
- 所持キャラ一覧（アイコン、属性、今日の天気ボーナスが付いているか）を出す。
- 詳細: 画像、説明文、HP/ATK/DEF/SPD（内訳: 基礎・アイテム・被り・天気）、バフ性能、ギミック、チェック/リターン/必殺技の回数。
- 出撃キャラに設定できる。

### F-07 アイテム強化
- キャラと同じ属性のアイテムを個数を指定して使い、ステータスを上げる。
- 上限: HP 20 / ATK 16 / DEF 15 / SPD 10 個。

### F-08 設定・その他
- BGM・SE の音量、名前変更、クレジット、問い合わせ先リンク。

## 4. バトル仕様（フェーズ 1 で実装するルール）

`01_legacy-analysis.md` §2 のルールをそのまま使う。要点:

1. 1 ターンの処理順: 【先制コマンド（防御 / 防御バフ）】→【敵の行動】→【プレイヤーの攻撃・攻撃バフ】
2. 敵の行動は `enemyTurns[turn]` の固定の並び。最終ターンは必殺技（ATK×100）。
3. チェック: 最大 2 回。ターンを消費しない。同じターンは登録できない。
4. リターン: 最大 1 回。ターン番号と敵の行動の進み具合だけ戻す。**HP・バフ・デバフ・属性は戻さない**。戻ったらチェックポイントは全部消える。
5. 必殺技: 条件を満たしたら、前後 2 ターン（計 5 ターン）の敵の行動から 1 つを 攻撃 / 防御 / 攻撃バフ / 防御バフ / 挑発 に書き換える。最大 1 回。
6. ビリビリの判定（50%）には**サーバが発行した乱数シード**を使う（再現と検証のため）。
7. 連戦（I → I2）: 1 体目の HP が 0 になったら、同じバトルの中で 2 体目に入れ替わる。プレイヤーの HP・バフ・リターン / 必殺技の使用回数は引き継ぎ、敵・ターン・チェックポイントはリセットする。
8. 数値の丸め・乱数・処理順などの細かいルールは `spec/battle/README.md` を正とする。

### 旧作のバグの扱い
| 旧作のバグ | リメイクでの扱い |
|---|---|
| `GetEnemyDefenceDebuffCount()` が攻撃デバフの値を返す | 修正する（防御デバフの値を使う） |
| 乱数が時刻シード | シード付きの乱数に変える |

### サーバ検証の流れ（改ざん対策）
```
1. クライアント → POST /quests/{id}/sessions        … サーバが sessionId と乱数シードを発行
2. クライアントでバトル（通信なし。オフラインでも進められる）
3. クライアント → POST /quest-sessions/{id}/result  … コマンドのログを送る
4. サーバがログを同じルールで再生（リプレイ）する → 勝っていれば報酬を付与して結果を返す
```
→ **バトルのルールはフロントとサーバの両方に必要**。持ち方は D-1 で決めた（下記）。

### ルールの実装方式（D-1 決定: B 案）
- フロント（AI）とサーバ（オーナー）が**それぞれ実装する**。コードは共有しない。
- 両者が同じ結果を出すことは、**共通のゴールデンテスト**（入力 → 期待する結果の JSON）で保証する。
- ゴールデンテストは OpenAPI と同じく**フロントとバックの契約**として扱う。
  - AI が旧作の仕様（`01_legacy-analysis.md`）から作り、オーナーがレビューして確定する。
  - 置き場所は `api/` の外（【仮】リポジトリ直下の `spec/battle/`）。
  - ケース: 全クエストの勝ちルート、各コマンド・敵行動の単体ケース、境界値（ダメージ 0、HP 半分ちょうど、必殺技の発動ターン境界、最終ターンなど）、リターン・必殺技の組み合わせ。
- ずれやすい点を仕様で固定する。
  - **数値の丸め**: ×1.25 / ×0.75 / ×0.8 / ×0.2 の計算で、どこで整数にするか（切り捨て等）。旧作 C# の型（int / float）を確認して決める。
  - **乱数**: シード付き乱数のアルゴリズム（【仮】mulberry32）と、呼び出す順番・回数。
- 二重実装のコストはあるが、ルールの規模が小さく（コマンド 7 種・敵行動約 15 種）許容できる。フェーズ 2 の PvP でも同じ方式を取る。

## 9. フロント技術構成（D-2 決定を受けて / フロントは AI 担当なので細部は実装時に調整）

| 領域 | 採用 | メモ |
|---|---|---|
| 言語・ビルド | TypeScript / Vite | `web/` の中は設定ファイルも TS で書く |

| API クライアント | OpenAPI から型を生成（openapi-typescript ＋ openapi-fetch） | OpenAPI はフロントとバックの約束 |
| テスト | Vitest（エンジン単体とゴールデンテスト）、Playwright（画面の E2E） | ゴールデンテストは `spec/battle/` の JSON を読んで実行 |
| 開発用のモック | MSW | API が完成する前に、OpenAPI どおりの仮レスポンスでフロントを進める |
| Web 配信 | PWA（vite-plugin-pwa） | ホーム画面に追加できる |
| ストア配信（1.5） | Capacitor | Android はローカル（WSL / Windows）でビルド。**iOS は Mac が無いのでクラウドでビルド**（Codemagic か GitHub Actions の macOS ランナー）。Apple Developer Program（年額）への登録が必要 |
| 素材 | `legacy/unity/Assets/素材` から変換して移す（PNG → WebP、WAV → OGG/M4A）。変換は `legacy/tools/` の Python スクリプトで行う | |
| 置き場所 | 【仮】リポジトリ直下の `web/` | `api/`（オーナー）と分ける |

## 10. マスタデータと素材の配信（D-6 決定: 2026-09-25）

新しいキャラ・クエスト・イベントは、アプリを更新せずにデータの追加だけで増やせるようにする。

```
正（編集する場所）   spec/master/*.json（git・PR でレビュー）      素材の元ファイル（git の外）
        │ デプロイ時に api が DB へ投入                                 │ legacy/tools の変換スクリプト
        ▼                                                                  ▼
配信                 api の DB → GET /master/version・GET /master     同梱素材: web/ にコミット
                                                                     取得素材: 静的ホスティング（後で CDN）
        ▼
クライアント          起動時にバージョンを確認し、新しければマスタを取り直す
                     素材はマスタに書かれたキーで必要なときに取得してキャッシュする
```

### マスタデータ
- **正は `spec/master/*.json`**。変更は PR でレビューする。web・api・ゴールデンテストが同じものを参照する。
- api はデプロイ時に DB へ投入（seed）し、DB から配信する。DB への投入方法・テーブル設計はオーナーが決める。
- `legacy/data` を元に作る（移行作業はこれから）。

### 素材
| 種類 | 例 | 置き場所 |
|---|---|---|
| 同梱素材 | タイトル・共通 UI・効果音（起動に必要なもの） | 変換後のファイルを `web/` にコミットする |
| 取得素材 | キャラの画像・クエスト・BGM など（増えていくもの） | 静的ホスティングの素材用の場所（フェーズ 1 は web と同じサーバー、ストア配信の頃に ストレージ＋CDN へ） |
| 元ファイル | 変換前の PNG・WAV | git の外（`legacy/unity` とバックアップ） |

- 取得素材は、変換スクリプトが出力したものを手元から手でアップロードする。変換後の素材の一覧（キー・ハッシュ）は git で管理する。
- マスタには素材の**パスではなくキー**（例: `characters/A/main.webp`）を書く。置き場所の基点 URL は設定で切り替える。
- ファイル名にハッシュを含め、長くキャッシュできるようにする。
- バトル画面に入る前に、その戦闘で使う素材を先読みする。

### 更新とアプリの互換性
- 起動時に `GET /master/version` でマスタのバージョンを確認し、手元より新しければ `GET /master` で丸ごと取り直す（150KB 程度）。
- ルールそのもの（新しいギミックなど）が変わったときは、**必要なアプリの最低バージョン**を上げる。古いアプリは更新を促す画面を出す。
- データの追加だけで増やせるのは既存のルールで動くもの（キャラ・クエスト・イベント）。新しいルールは web と api の両方のエンジンの更新が必要。
